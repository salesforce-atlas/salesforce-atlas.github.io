    Data Modeling & Governance¶

    Data Modeling Fundamentals¶

    Entity Relationship Design¶

    Standard Objects¶

    • Leverage standard objects when possible
    • Understand standard object relationships
    • Extend with custom fields
    • Follow naming conventions

    Custom Objects¶

    • Use when standard objects don't fit
    • Consider namespace if packaging
    • Define clear object purpose
    • Plan for scalability

    Relationship Types¶

    Lookup Relationship¶

    • Loosely coupled
    • No cascade delete
    • Independent records
    • Up to 40 per object
    • Use for flexible associations

    Master-Detail Relationship¶

    • Tightly coupled
    • Cascade delete
    • Roll-up summary fields
    • Sharing inherited from master
    • Use for ownership/containment

    Many-to-Many (Junction Object)¶

    • Two master-detail relationships
    • Enables M:M associations
    • Example: Student-Class-Enrollment
    • Consider reporting requirements

    External Lookup¶

    • Relates to external objects
    • Salesforce Connect
    • Standard and External ID matching

    Hierarchical Relationship¶

    • User and Account objects only
    • Self-referencing
    • Organizational hierarchy
    • Role hierarchy integration

    Data Model Patterns¶

    Account Model Patterns¶

    Person Accounts¶

    • B2C scenarios
    • Individual consumers
    • Merged Account and Contact
    • Different relationship model

    Business Accounts¶

    • B2B scenarios
    • Organizations
    • Multiple contacts per account
    • Account hierarchies

    Household Account Model¶

    • Financial services
    • Family relationships
    • Shared household data
    • Individual and collective views

    Activity Data Model¶

    • Tasks and Events
    • Activity Timeline
    • Custom activities
    • Activity relationships

    Data Volumes & Limits¶

    Storage Limits¶

    • Data storage (per org and per license)
    • File storage
    • Big objects for massive data (billions of records)

    Object Limits¶

    • 800 custom objects per org (Developer)
    • 2000+ in Enterprise/Unlimited
    • Custom fields per object
    • Relationship limits

    Query Optimization¶

    • Selective queries (filtering <10% of records)
    • Custom indexes
    • Skinny tables
    • Query plan analysis

    Data Migration Strategies¶

    Migration Approaches¶

    Big Bang Migration¶

    • One-time full migration
    • System downtime
    • Faster implementation
    • Higher risk

    Phased Migration¶

    • Gradual data transfer
    • Parallel systems
    • Lower risk
    • Longer timeline

    Hybrid Approach¶

    • Critical data first
    • Historical data batched
    • Balanced risk and timeline

    Data Migration Tools¶

    Native Tools¶

    • Data Loader
    • Data Import Wizard
    • Workbench

    Third-Party Tools¶

    • Informatica
    • MuleSoft
    • Jitterbit
    • DBAmp

    Migration Best Practices¶

    1. Data Assessment: Profile source data quality
    2. Data Cleansing: Clean before migration
    3. Mapping: Document field mappings
    4. Transformation: Define transformation rules
    5. Validation: Test with sample data
    6. Deduplication: Implement matching rules
    7. Rollback Plan: Prepare for failures
    8. Monitoring: Track progress and errors

    • Single source of truth

    • Customer 360

    MDM Patterns¶

    • Consolidation: Centralize from multiple sources
    • Registry: Metadata about data locations
    • Coexistence: Distributed with synchronization

    • Completeness: All required fields populated
    • Consistency: Same data across systems
    • Timeliness: Up-to-date information
    • Validity: Adheres to business rules
    • Uniqueness: No duplicates

    • Simpler maintenance
    • Shared resources
    • Unified reporting

    Multi-Org Architecture¶

    • Data isolation
    • Regional compliance
    • Performance isolation
    • Complex integration

    Considerations¶

    • Data residency requirements
    • Compliance needs

    • User access patterns
    • Integration complexity

    Big Objects¶

    When to Use¶

    • Billions of records
    • Historical data
    • Archive scenarios
    • Analytics and reporting

    Limitations¶

    • No triggers
    • No flows
    • No standard UI
    • Async SOQL only

    Use Cases¶

    • Audit trails
    • Historical metrics
    • IoT data
    • Transaction history

    External Objects¶

    Salesforce Connect¶

    • Virtual data integration
    • No data storage in Salesforce
    • Real-time external access
    • OData protocol

    Use Cases¶

    • ERP data access
    • Legacy system integration
    • Data lake queries
    • Third-party services

    • Tab visibility

    Record-Level Security¶

    • Role hierarchy
    • Sharing rules
    • Manual sharing
    • Teams

    Data Privacy¶

    • GDPR compliance
    • Right to be forgotten
    • Data portability
    • Consent management
    • Individual object (Data Privacy)

    Data Retention & Archiving¶

    Retention Policies¶

    • Legal requirements
    • Business requirements
    • Storage optimization
    • Performance considerations

    Archiving Strategies¶

    • Field History Tracking: 18-24 months
    • Deleted Records: Recycle bin (15 days)
    • Long-term Storage: Big Objects, external systems

    Tools¶

    • Salesforce Big Objects
    • External archiving solutions
    • Data warehouse integration
    • S3/cloud storage

    Schema Design Best Practices¶

    1. Normalize: Reduce redundancy
    2. Denormalize: Optimize queries when needed
    3. Index Strategy: Selective indexing
    4. Archive Strategy: Move old data
    5. Scalability: Design for growth
    6. Flexibility: Allow for changes

    Common Data Modeling Mistakes¶

    ❌ Avoid: - Over-normalization (too many lookups) - Circular references - Excessive formula fields - Poor relationship choices - Ignoring scalability - No data retention strategy

    ✅ Do: - Balance normalization with performance - Plan relationship structure carefully - Use roll-up summaries efficiently - Choose appropriate relationship types - Plan for data volume growth - Implement archiving early
