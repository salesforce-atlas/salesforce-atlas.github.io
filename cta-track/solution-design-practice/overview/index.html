    Solution Design Practice Overview¶

    From Theory to Practice¶

    This section bridges the gap between architectural knowledge and practical solution design. Here you'll practice designing real Salesforce solutions that balance business requirements, technical constraints, and stakeholder needs.

    What is Solution Design Practice?¶

    Solution Design Practice is the hands-on application of architectural principles to create comprehensive, production-ready Salesforce solutions. It involves:

    • Translating business requirements into technical solutions
    • Making informed trade-off decisions
    • Designing scalable and maintainable architectures
    • Documenting design decisions
    • Communicating solutions to stakeholders

    This Section's Focus¶

    Unlike the Architect Readiness section (which builds foundational thinking), this section emphasizes practical design exercises that mirror real CTA scenarios.

    Learning Objectives¶

    By the end of this section, you should be able to:

    1. Analyze Requirements

    2. Extract key business and technical requirements

    3. Identify constraints and assumptions
    4. Prioritize must-haves vs. nice-to-haves

    5. Recognize gaps and ambiguities

    6. Design Comprehensive Solutions

    7. Create data models for complex business processes

    8. Design integration architectures
    9. Plan security and governance frameworks

    10. Build scalable, performant solutions

    11. Document Decisions

    12. Explain design rationale

    13. Articulate trade-offs
    14. Justify technology choices

    15. Create clear diagrams

    16. Communicate Effectively

    17. Present solutions to stakeholders

    18. Defend design decisions
    19. Handle objections
    20. Adapt communication style to audience

    Section Structure¶

    1. CRM & Data Modeling Scenarios¶

    Focus: Designing data models for complex business processes

    Topics covered:

    • Account and contact hierarchies
    • Custom objects for unique business needs
    • Relationships and data integrity
    • Data migration strategies
    • Large data volume handling

    Practice approach: Work through 5-10 scenarios, each building complexity

    2. Integration Blueprints¶

    Focus: Designing enterprise integration architectures

    Topics covered:

    • Integration patterns and best practices
    • API design and management
    • Event-driven architectures
    • Middleware selection
    • Error handling and monitoring

    Practice approach: Create detailed integration blueprints with technology recommendations

    3. Governance & Security Cases¶

    Focus: Implementing robust security and compliance frameworks

    Topics covered:

    • Security model design
    • Compliance requirements (GDPR, HIPAA, SOX)
    • Data governance frameworks
    • Audit and monitoring
    • Risk mitigation

    Practice approach: Design security architectures for regulated industries

    4. Stakeholder Communication¶

    Focus: Presenting and defending solutions

    Topics covered:

    • Executive presentations
    • Technical deep-dives
    • Handling objections
    • Building consensus
    • Change management

    Practice approach: Mock presentations and Q&A sessions

    Practice Methodology¶

    Step 1: Analyze (20 minutes)¶

    • Read the scenario thoroughly
    • Highlight key requirements
    • List assumptions
    • Identify constraints
    • Note questions for clarification

    Step 2: Design (40 minutes)¶

    • Sketch data model
    • Draw integration architecture
    • Plan security model
    • Consider scalability
    • Document trade-offs

    Step 3: Document (10 minutes)¶

    • Create clean diagrams
    • Write key decisions
    • List risks and mitigations
    • Prepare talking points

    Step 4: Present (15 minutes)¶

    • Explain business context
    • Walk through solution
    • Highlight key decisions
    • Discuss trade-offs
    • Open for questions

    Step 5: Defend (30 minutes)¶

    • Answer clarifying questions
    • Defend design choices
    • Acknowledge alternatives
    • Adjust if needed
    • Demonstrate flexibility

    Design Principles¶

    1. Business-First Thinking¶

    Start with business outcomes, then work backwards to technical solutions.

    ❌ "We should use Platform Events because they're cool" ✅ "To meet the real-time requirement while staying within governor limits, Platform Events provide asynchronous, scalable event processing"

    2. Right-Sized Solutions¶

    Match complexity to requirements, avoid over-engineering.

    ❌ Building custom middleware when standard APIs suffice ✅ Using standard REST APIs for simple point-to-point integration

    3. Scalability by Design¶

    Plan for growth from day one.

    ❌ Designing for current 100 users without considering future growth ✅ Architecting for 10,000 users even if starting with 100

    4. Security & Compliance¶

    Bake in security, don't bolt it on later.

    ❌ Adding encryption after go-live ✅ Designing with Shield Platform Encryption from the start

    5. Maintainability¶

    Future developers will thank you (or curse you).

    ❌ Complex, undocumented custom code ✅ Clear, well-documented solutions following best practices

    Common Design Patterns¶

    Data Model Patterns¶

    • Master-Detail for strict parent-child: Order → Order Line Items
    • Lookup for flexible relationships: Account → Partner Account
    • Junction objects for many-to-many: Campaigns ↔ Opportunities
    • Extension objects for scalability: Account → Account_Details__c

    Integration Patterns¶

    • Request-Reply: Synchronous API calls
    • Fire-and-Forget: Asynchronous messaging
    • Batch Data Sync: Nightly ETL jobs
    • Event-Driven: Platform Events, Change Data Capture

    Security Patterns¶

    • Layered security: Profiles + Permission Sets + Sharing
    • Least privilege: Grant minimum necessary access
    • Data classification: Identify and protect sensitive data
    • Audit everything: Field History, Event Monitoring

    Design Artifacts¶

    What to Create¶

    1. Solution Architecture Diagram¶

    • High-level system overview
    • Integration points
    • Data flow
    • Security boundaries

    2. Data Model Diagram¶

    • Objects and relationships
    • Key fields
    • Master-detail vs. lookup
    • Custom vs. standard objects

    3. Integration Architecture¶

    • Systems involved
    • Integration patterns
    • Data flow direction
    • Error handling

    4. Security Model¶

    • OWD settings
    • Sharing rules
    • Profiles and permission sets
    • Data encryption

    5. Decision Log¶

    • Key decisions made
    • Alternatives considered
    • Trade-offs analyzed
    • Rationale documented

    Whiteboarding Tips¶

    • Plan before drawing: Know what goes where
    • Use consistent symbols: Define legend upfront
    • Left to right flow: Natural reading direction
    • Label everything: No mystery boxes
    • Leave space: Room for additions during Q&A
    • Use color purposefully: Not just decoration

    Practice Schedule¶

    Weekly Practice Routine¶

    Monday: Data modeling scenario (60 min) - Practice designing complex data models - Focus on relationships and scalability

    Wednesday: Integration scenario (75 min) - Full CTA-style scenario - Timed practice with analysis + design

    Friday: Security & governance (45 min) - Focus on compliance requirements - Practice articulating security decisions

    Weekend: Presentation practice (2 hours) - Present completed scenarios to study group - Receive feedback - Practice Q&A defense

    Evaluation Criteria¶

    Rate your solutions on:

    Technical Soundness (30%)¶

    • [ ] Meets all requirements
    • [ ] Scalable and performant
    • [ ] Follows best practices
    • [ ] Technically feasible

    Design Quality (25%)¶

    • [ ] Right-sized (not over/under-engineered)
    • [ ] Maintainable
    • [ ] Well-documented
    • [ ] Clear diagrams

    Business Alignment (20%)¶

    • [ ] Addresses business problem
    • [ ] Delivers value
    • [ ] Cost-effective
    • [ ] Realistic timeline

    Communication (15%)¶

    • [ ] Clear presentation
    • [ ] Explains rationale
    • [ ] Handles questions well
    • [ ] Adapts to audience

    Risk Management (10%)¶

    • [ ] Identifies risks
    • [ ] Proposes mitigations
    • [ ] Has contingency plans
    • [ ] Considers constraints
