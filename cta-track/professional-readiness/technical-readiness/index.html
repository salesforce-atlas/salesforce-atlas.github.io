    Architecture Design Principles¶

    Fundamental Principles¶

    1. Separation of Concerns¶

    • Divide solution into distinct modules
    • Each module handles specific functionality
    • Reduces complexity and improves maintainability
    • Examples: Service layer, data layer, presentation layer

    2. Single Responsibility Principle¶

    • Each component should have one reason to change
    • Avoid mixing business logic with UI logic
    • Keep triggers focused on orchestration
    • Separate concerns across classes

    3. DRY (Don't Repeat Yourself)¶

    • Eliminate code duplication
    • Create reusable components
    • Centralize business logic
    • Use inheritance and composition

    4. SOLID Principles¶

    S - Single Responsibility¶

    • One class, one purpose

    ¶

    O - Open/Closed - Open for extension, closed for modification

    L - Liskov Substitution¶

    • Subtypes must be substitutable for base types

    I - Interface Segregation¶

    • Many specific interfaces over one general interface

    D - Dependency Inversion¶

    • Depend on abstractions, not concretions

    Salesforce-Specific Design Patterns¶

    Trigger Pattern¶

    Best Practices: - One trigger per object - Trigger handler pattern - Bulkified operations - Avoid SOQL/DML in loops

    Service Layer Pattern¶

    • Business logic in service classes
    • Called from triggers, controllers, batch jobs
    • Promotes reusability
    • Centralizes complex operations

    Domain Layer Pattern¶

    • Object-specific logic
    • Encapsulates SObject behavior
    • Domain classes for business entities
    • Reduces coupling

    Selector Layer Pattern¶

    • SOQL query centralization
    • Consistent query patterns
    • Security enforcement (with sharing)
    • Query optimization

    Scalability Considerations¶

    Horizontal Scalability¶

    • Design for multiple orgs/instances
    • Multi-tenant architecture
    • Packaging strategies
    • Namespace considerations

    Vertical Scalability¶

    • Handle increasing data volumes
    • Optimize queries with indexes
    • Use skinny tables where appropriate
    • Archive old data

    Performance Optimization¶

    • Lazy loading
    • Caching strategies
    • Asynchronous processing
    • Query optimization

    Governor Limits Compliance¶

    Design Strategies¶

    1. Bulkification: Handle collections, not single records
    2. Asynchronous Apex: Use @future, Batch, Queueable
    3. Platform Events: Decouple processes
    4. External Processing: Offload to external systems
    5. Caching: Reduce redundant queries

    Limit Awareness¶

    • SOQL queries (100/200)
    • DML statements (150)
    • Heap size (6MB/12MB)
    • CPU time (10s/60s)
    • Callouts (100)

    Multi-Cloud Architecture¶

    Design Considerations¶

    • Shared data model across clouds
    • Integration touchpoints
    • User experience consistency
    • License optimization
    • Feature parity

    Common Patterns¶

    • Sales Cloud + Service Cloud
    • Sales Cloud + Marketing Cloud + Commerce Cloud
    • Industry Cloud + Core Clouds
    • Platform + Experience Cloud

    • Complex business domains
    • Independent deployment needs
    • Different scaling requirements
    • Team autonomy

    Implementation¶

    • Platform events for communication
    • API-first design
    • Bounded contexts
    • Independent data models

    Design Decision Framework¶

    Evaluation Criteria¶

    1. Functional Requirements: Does it meet needs?
    2. Non-Functional Requirements: Performance, security, scalability
    3. Cost: License, development, maintenance
    4. Complexity: Implementation and support effort
    5. Risk: Technical and business risks
    6. Governance: Compliance and standards

    Documentation¶

    • Architecture Decision Records (ADRs)
    • Design rationale
    • Trade-offs considered
    • Impact analysis

    Common Anti-Patterns¶

    Avoid These¶

    ❌ Hard-coding IDs ❌ SOQL/DML in loops ❌ Tight coupling between components ❌ Monolithic triggers ❌ Ignoring sharing rules ❌ Poor error handling ❌ Lack of testing ❌ Over-engineering

    Do This Instead¶

    ✅ Use custom metadata/settings ✅ Bulkify operations ✅ Loose coupling with interfaces ✅ Trigger handler pattern ✅ Enforce security ✅ Comprehensive error handling ✅ Test-driven development ✅ Right-sized solutions

    Case Study Example¶

    Scenario¶

    Global company needs multi-region sales solution

    Design Approach¶

    1. Single org vs. multi-org: Evaluate based on data residency
    2. Data model: Shared objects across regions
    3. Sharing model: Territory-based sharing
    4. Integration: Regional ERP systems
    5. Reporting: Consolidated dashboards
    6. Security: Regional admin delegation

    Architecture Decisions¶

    • Single production org (data residency not required)
    • Custom objects for regional-specific data
    • Territory management for access control
    • MuleSoft for ERP integration
    • Tableau for cross-region analytics

    Best Practices¶

    1. Start Simple: Don't over-architect
    2. Iterate: Evolutionary architecture
    3. Document: Capture decisions and rationale
    4. Review: Peer and stakeholder reviews
    5. Prototype: Validate assumptions early
    6. Monitor: Track performance and usage
    7. Refactor: Continuous improvement
