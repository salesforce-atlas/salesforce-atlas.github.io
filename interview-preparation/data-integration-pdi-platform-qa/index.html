    📚 Fundamentals & Platform Basics¶

    Q: What is Pentaho Data Integration (PDI) and what are its key components?¶

    A: Pentaho Data Integration, also known as Kettle, is an open-source ETL (Extract, Transform, Load) tool that enables data integration across various sources and destinations. It provides a visual development environment for designing data pipelines.

    Key Components:

    Spoon:

    • Definition: Graphical design interface for creating transformations and jobs
    • Purpose: Visual development environment
    • Features: Drag-and-drop interface, step configuration, preview data
    • Platform: Desktop application (Windows, Linux, macOS)

    Pan:

    • Definition: Command-line tool for executing transformations
    • Usage: pan.sh -file=/path/to/transformation.ktr -level=Basic
    • Purpose: Production execution of transformations
    • Features: Headless execution, logging, parameter passing

    Kitchen:

    • Definition: Command-line tool for executing jobs
    • Usage: kitchen.sh -file=/path/to/job.kjb -level=Detailed
    • Purpose: Production execution of jobs
    • Features: Scheduling integration, error handling, job orchestration

    Carte:

    • Definition: Web server for remote execution
    • Purpose: Distributed processing and clustering
    • Features: REST API, load balancing, remote monitoring

    Key Concepts:

    Transformations (.ktr files):

    • Single-threaded execution within each step
    • Multi-threaded execution across steps
    • Data flows between steps in rowsets
    • Used for data processing and transformation

    Jobs (.kjb files):

    • Sequential or conditional execution
    • Orchestrate multiple transformations
    • Control flow and error handling
    • Scheduling and workflow management

    Steps vs Entries:

    • Steps: Building blocks in transformations (e.g., Table Input, Filter Rows)
    • Entries: Building blocks in jobs (e.g., Start, Transformation, Success)

    Architecture:

    1
2
3
    Data Sources → [Extraction] → [Transformation] → [Loading] → Target Systems
                    ↓              ↓                ↓
                 Input Steps   Processing Steps  Output Steps

    Use Cases:

    Data Migration:

    • Move data between systems
    • Database upgrades
    • System consolidations
    • Legacy system decommissioning

    Data Warehousing:

    • ETL processes for data warehouses
    • Dimension and fact table loading
    • Slowly changing dimensions (SCD)
    • Data mart population

    Data Integration:

    • Real-time data synchronization
    • Master data management
    • API integration
    • File processing automation

    Data Quality:

    • Data cleansing and standardization
    • Duplicate detection
    • Validation and error handling
    • Data profiling

    Deployment Models:

    • On-Premises: Traditional server installation
    • Cloud: AWS, Azure, Google Cloud deployments
    • Hybrid: Mix of on-premises and cloud
    • Containerized: Docker and Kubernetes

    Advantages:

    ✅ Visual development environment

    ✅ Wide range of supported data sources

    ✅ Active community and extensive documentation

    ✅ No per-row licensing costs

    ✅ Scalable for large data volumes

    ✅ Cross-platform compatibility

    Limitations:

    ⚠️ Memory consumption for large datasets

    ⚠️ Limited real-time streaming capabilities

    ⚠️ Performance dependent on system resources

    ⚠️ Complexity increases with large projects

    Best Practices:

    ✅ Use consistent naming conventions

    ✅ Document transformations and jobs

    ✅ Implement error handling

    ✅ Use parameters for flexibility

    ✅ Version control (Git) for .ktr and .kjb files

    ✅ Test thoroughly in development environment

    Q: What is the difference between a Transformation and a Job in PDI?¶

    A: Transformations and Jobs are the two primary building blocks in PDI, each serving distinct purposes in the data integration process.

    Transformations (.ktr):

    Characteristics:

    • Execution: Parallel, multi-threaded processing
    • Data Flow: Rows flow between steps continuously
    • Purpose: Data extraction, transformation, and loading
    • Building Blocks: Steps (Input, Transform, Output, Utility)
    • Flow Type: Data flow (rowsets)

    Execution Model:

    1
2
3
    [Table Input] → [Filter Rows] → [Calculator] → [Table Output]
      ↓               ↓              ↓              ↓
   (Thread 1)     (Thread 2)    (Thread 3)    (Thread 4)

    Common Steps:

    Input Steps:

    • Table Input (database queries)
    • Text File Input (CSV, TXT)
    • Excel Input (XLS, XLSX)
    • JSON Input
    • XML Input
    • REST Client

    Transform Steps:

    • Select Values (rename, reorder columns)
    • Filter Rows (conditional filtering)
    • Calculator (calculations, functions)
    • String Operations (concatenate, replace)
    • Add Sequence (generate IDs)
    • Sort Rows (ordering data)

    Output Steps:

    • Table Output (database inserts/updates)
    • Text File Output
    • Insert/Update (upsert operations)
    • Excel Output
    • JSON Output

    Jobs (.kjb):

    Characteristics:

    • Execution: Sequential (unless parallel specified)
    • Control Flow: Conditional execution paths
    • Purpose: Workflow orchestration
    • Building Blocks: Entries (Start, Transformations, Checks, Mail)
    • Flow Type: Control flow (success/failure)

    Execution Model:

    1
2
3
4
5
    [Start] → [Check Files] → [Transformation 1] → [Success Check]
                                ↓ (Success)          ↓
                          [Transformation 2]  → [Send Email]
                                ↓ (Failure)
                           [Error Handler]

    Common Entries:

    Start Entries:

    • Start (entry point)

    General Entries:

    • Transformation (execute .ktr)
    • Job (execute nested .kjb)
    • Shell (execute scripts)
    • SQL (run SQL scripts)
    • Mail (send notifications)

    File Management:

    • Copy Files
    • Delete Files
    • File Exists
    • Wait for File

    Flow Control:

    • Success (next on success)
    • Failure (next on failure)
    • Unconditional (always execute)
    • Evaluation (conditional)

    Comparison:

    When to Use Transformations:

    • Processing data records
    • Reading from sources
    • Transforming data
    • Writing to destinations
    • Data validation
    • Column calculations

    When to Use Jobs:

    • Orchestrating multiple transformations
    • Conditional execution logic
    • File system operations
    • Email notifications
    • Error handling workflows
    • Scheduling and automation

    Key Differences Summary:

    Transformations:

    • ✅ Parallel execution (faster)
    • ✅ Row-based processing
    • ✅ Data transformations
    • ❌ Limited control flow
    • ❌ Cannot call other transformations directly

    Jobs:

    • ✅ Control flow orchestration
    • ✅ Error handling
    • ✅ Conditional execution
    • ✅ Can call transformations and jobs
    • ❌ Sequential by default (slower)

    Best Practices:

    ✅ Use transformations for data processing

    ✅ Use jobs for workflow orchestration

    ✅ Keep transformations focused on single tasks

    ✅ Use jobs for complex conditional logic

    ✅ Implement error handling in jobs

    ✅ Pass parameters from jobs to transformations

    ✅ Use meaningful names for both

    Q: How does data flow work in PDI transformations?¶

    A: Understanding data flow in PDI transformations is crucial for designing efficient ETL processes. PDI uses a unique parallel processing model that differs from traditional sequential ETL tools.

    Data Flow Characteristics:

    Parallel Processing:

    • Each step runs in its own thread
    • Multiple steps execute simultaneously
    • Data flows through rowsets (buffers)
    • Non-blocking architecture

    Rowset Buffers:

    • Default buffer size: 10,000 rows
    • Configurable per transformation
    • Memory-based data transfer
    • First-In-First-Out (FIFO) queue

    Execution Model:

    1
2
3
4
5
6
7
8
9
    Source Step (Thread 1)
    ↓ [Rowset Buffer]
Transform Step 1 (Thread 2)
    ↓ [Rowset Buffer]
Transform Step 2 (Thread 3)
    ↓ [Rowset Buffer]
Target Step (Thread 4)

All threads execute simultaneously!

    Hops (Connections):

    Types of Hops:

    Main Output Hop:

    • Primary data flow path
    • Black line in Spoon
    • Most common connection type

    Error Handling Hop:

    • Red line in Spoon
    • Routes error rows to error handling
    • Configured in step properties

    Target Steps Hop:

    • Used for specific routing
    • Multiple output paths from single step

    Data Distribution:

    Copy Rows to Result:

    • Passes data to next transformation in job
    • Used for transformation chaining
    • Memory-based storage

    Get Rows from Result:

    • Receives data from previous transformation
    • Complements Copy Rows to Result

    Distribution Methods:

    • Round Robin: Evenly distribute rows
    • Load Balanced: Based on processing time
    • Random: Random distribution

    Performance Implications:

    Buffer Size Configuration:

    1
2
3
    # In transformation settings or spoon.sh/bat
KETTLE_MAX_BUFFER_SIZE=10000
KETTLE_MAX_BUFFER_LINE_SIZE=5000

    Memory Usage:

    • Each rowset buffer consumes memory
    • More steps = more memory required
    • Large buffers = higher memory consumption
    • Balance between performance and resources

    Blocking Steps:

    Steps that Block Data Flow:

    • Sort Rows: Must read all rows before sorting
    • Group By: Must accumulate groups
    • Unique Rows: Must see all rows to find duplicates
    • Merge Join: Requires sorted input

    Impact:

    1
2
3
4
    [Input: 1M rows] → [Sort Rows] → [Output]
                      ↑
              (Blocks until all rows read)
              (High memory usage)

    Non-Blocking Alternative:

    1
2
3
4
    [Input: 1M rows] → [Filter Rows] → [Output]
                      ↑
              (Streams through immediately)
              (Low memory usage)

    Data Flow Optimization:

    Best Practices:

    ✅ Minimize blocking steps

    ✅ Use appropriate buffer sizes

    ✅ Filter early to reduce data volume

    ✅ Sort data at source when possible

    ✅ Monitor memory usage

    ✅ Use step copies for parallel processing

    ✅ Avoid unnecessary transformations

    Monitoring Data Flow:

    Preview Feature:

    • Right-click step → Preview
    • Shows sample data at that point

    Logging:

    Common Issues:

    Slow Performance:

    • Too many blocking steps
    • Large buffer sizes
    • Insufficient memory
    • Complex transformations

    • Too many concurrent steps
    • Blocking steps with large datasets
    • Insufficient heap size

    Data Loss:

    • Missing error handling hops
    • Incorrect filtering
    • Buffer overflow (rare)
