    Q: What is the Salesforce multi-tenant architecture and how does it affect development?¶

    A: Salesforce multi-tenant architecture means multiple customers (tenants) share the same infrastructure and application code while maintaining data isolation. This fundamentally impacts how developers must write code.

    Key Characteristics:

    • Shared Resources: All orgs run on shared servers with shared database tables
    • Metadata-Driven: Customizations are stored as metadata, not hard-coded
    • Governor Limits: Enforced to prevent any single tenant from monopolizing resources
    • Universal Upgrades: All customers automatically receive platform upgrades

    Development Implications:

    • Must write bulkified code to handle multiple records
    • Cannot use infinite loops or unbounded queries
    • Must respect governor limits in all code
    • Cannot make assumptions about data volume

        if (!contactsByAccount.containsKey(con.AccountId)) {
            contactsByAccount.put(con.AccountId, new List<Contact>());
        }
        contactsByAccount.get(con.AccountId).add(con);
    }
}

    Q: What is the difference between declarative and programmatic customization in Salesforce?¶

    A: Declarative customization uses point-and-click tools without writing code, while programmatic customization involves writing Apex code, Lightning components, or Visualforce pages.

    Declarative Tools:

    • Process Builder/Flow: Automate business processes
    • Formula Fields: Calculate values dynamically
    • Validation Rules: Enforce data quality
    • Page Layouts: Control field visibility and arrangement
    • Record Types: Provide different business processes
    • Workflow Rules: Simple field updates and email alerts (legacy)

    Programmatic Tools:

    • Apex: Custom business logic and complex automation
    • Lightning Web Components (LWC): Modern UI components
    • Visualforce: Legacy UI framework
    • Apex Triggers: Complex record automation
    • Batch Apex: Process large data volumes

    Decision Criteria:

    Use Declarative When:

    • Standard functionality meets requirements
    • No complex business logic needed
    • Faster development time is priority
    • Non-developers need to maintain it

    Use Programmatic When:

    • Complex calculations or logic required
    • Integration with external systems needed
    • Declarative limits are exceeded
    • Custom UI components required
    • Performance optimization needed

    Best Practice:

    ✅ Always use declarative tools first (clicks, not code)

    ✅ Only write code when declarative tools cannot meet requirements

    ✅ Document why code was necessary instead of clicks

    Governor Limits:

    ⚠️ Declarative: 2,000 active Flow interviews, 5,000 time-based workflows

    ⚠️ Programmatic: 100 SOQL queries, 150 DML statements, 10 seconds CPU time per transaction

    Q: What are the different types of relationships in Salesforce and when should each be used?¶

    A: Salesforce supports four main types of relationships: Lookup, Master-Detail, Many-to-Many (Junction Objects), and External Lookup relationships.

    Relationship Types:

    Lookup Relationship:

    • Definition: Loosely coupled relationship between two objects
    • Cascade Delete: No automatic deletion of child records
    • Roll-Up Summary: Not available
    • Sharing: Child records have independent sharing rules
    • Use Case: Optional relationships like Account to Contact

    Master-Detail Relationship:

    • Definition: Tightly coupled relationship where child depends on parent
    • Cascade Delete: Child records automatically deleted with parent
    • Roll-Up Summary: Available on master object
    • Sharing: Child inherits sharing from master
    • Use Case: Order and Order Line Items

    Many-to-Many Relationship:

    • Definition: Created using junction object with two master-detail relationships
    • Implementation: Junction object connects two parent objects
    • Use Case: Students enrolled in multiple Classes

    External Lookup:

    • Definition: Links to records in external objects
    • Data Location: Data stored outside Salesforce
    • Use Case: Integration with external systems

    Relationship Limits:

    ⚠️ Maximum 2 master-detail relationships per object

    ⚠️ Maximum 40 total relationships per object

    ⚠️ Master-detail parent must be created before child

    Q: What is the Salesforce Order of Execution and why is it important for developers?¶

    A: The Salesforce Order of Execution is the sequence of operations that occur when a record is saved. Understanding this is critical for preventing conflicts between automation tools and ensuring predictable behavior.

    Complete Order of Execution:

    Phase 1 - Load & Validation:

    • Load the original record from database or initialize for insert
    • Load new values from UI or API
    • Run system validation rules
    • Execute Before triggers
    • Run custom validation rules

    Phase 2 - Save & Process:

    • Save record to database (not committed)
    • Execute After triggers
    • Execute assignment rules
    • Execute auto-response rules
    • Execute workflow rules (field updates)
    • Execute escalation rules

    Phase 3 - Post-Processing:

    • Execute roll-up summary fields
    • Execute Apex sharing recalculation
    • Execute criteria-based sharing rules
    • Execute Process Builder/Flow (if configured)
    • Execute entitlement rules
    • Execute cross-object workflow updates

    Phase 4 - Finalization:

    • Execute post-commit logic
    • Send email notifications
    • Execute asynchronous Apex (@future, Queueable, Batch)

    Critical Developer Considerations:

    Before Triggers:

    • Record not yet in database
    • Can modify field values before save
    • Use for field defaulting and validation

    After Triggers:

    • Record saved but not committed
    • Cannot modify current record
    • Use for related record operations

    Common Pitfalls:

    ❌ Modifying records in After triggers (not allowed)

    ❌ Not accounting for workflow field updates

    ❌ Recursive trigger issues

    ❌ Mixing Process Builder and triggers on same object

public class AccountTriggerHandler {

    private static Boolean isExecuting = false;

    // Prevent recursive execution
    public static void beforeInsert(List<Account> newAccounts) {
        if (isExecuting) return;
        isExecuting = true;

        for (Account acc : newAccounts) {
            // Set default values
            if (acc.Rating == null) {
                acc.Rating = 'Cold';
            }
        }

        isExecuting = false;
    }

    public static void afterInsert(List<Account> newAccounts) {
        if (isExecuting) return;
        isExecuting = true;

        // Create related records
        List<Contact> contacts = new List<Contact>();
        for (Account acc : newAccounts) {
            contacts.add(new Contact(
                AccountId = acc.Id,
                LastName = 'Default Contact',
                Email = 'contact@' + acc.Name.toLowerCase() + '.com'
            ));
        }
        insert contacts;

        isExecuting = false;
    }
}

    Best Practices:

    ✅ Use Before triggers for field updates on current record

    ✅ Use After triggers for operations on related records

    ✅ Implement recursion prevention mechanisms

    ✅ Document automation interactions

    ✅ Test with multiple automation tools active

    Governor Limits:

    ⚠️ Maximum trigger depth: 16 levels

    ⚠️ Maximum workflow field updates: 10 per record

    ⚠️ CPU timeout after recursive execution

    Q: What are Validation Rules and how do they differ from Triggers?¶

    A: Validation Rules are declarative formulas that prevent invalid data from being saved. They run before triggers and return custom error messages when conditions are not met.

    Validation Rule Components:

    Error Condition Formula:

    • Returns TRUE when data is invalid
    • Prevents record from being saved
    • Evaluated before triggers execute

    Error Message:

    • Displayed to user when validation fails
    • Can be field-specific or page-level

    Error Location:

    • Top of page (general error)
    • Specific field (field-level error)

    • Cross-object field validation
    • No queries or DML required
    • Non-developers need to maintain

    Use Triggers When:

    • Complex business logic required
    • Need to query related records
    • Multiple operations needed
    • Dynamic error messages required
    • Integration with external systems

    ✅ Consider user experience (don't over-validate)

    ❌ Don't create overly complex formulas

    Governor Limits:

    ⚠️ No hard limit on validation rules per object

    ⚠️ Formula complexity limit: 5,000 characters compiled

    ⚠️ Validation rules run on every record save

    Q: What is Apex and what are its key characteristics?¶

    A: Apex is Salesforce's proprietary, strongly-typed, object-oriented programming language that executes on the Salesforce platform. It's similar to Java and allows developers to add custom business logic to Salesforce applications.

    Key Characteristics:

    Strongly Typed:

    • Variables must be declared with specific data types
    • Type safety enforced at compile time
    • Prevents type-related runtime errors

    Object-Oriented:

    • Supports classes and objects
    • Inheritance through extends keyword
    • Interfaces for polymorphism
    • Encapsulation with access modifiers

    Multi-Tenant Aware:

    • Built-in governor limits enforcement
    • Automatic bulkification considerations
    • Cannot monopolize shared resources

    Integrated with Database:

    • Native SOQL and SOSL support
    • Built-in DML operations
    • Automatic transaction management

    Q: What are the different types of Salesforce APIs and when should each be used?¶

    A: Salesforce provides multiple APIs for different integration scenarios. Each API has specific use cases, advantages, and limitations.

    API Types:

    REST API:

    • Use Case: Mobile and web applications, lightweight integrations
    • Data Format: JSON or XML
    • Authentication: OAuth 2.0
    • Best For: CRUD operations on records, flexible queries

    SOAP API:

    • Use Case: Enterprise integrations, robust error handling
    • Data Format: XML
    • Authentication: Username/password or OAuth
    • Best For: Complex integrations requiring WSDL

    Bulk API:

    • Use Case: Loading or deleting large data sets (thousands to millions of records)
    • Data Format: CSV, JSON, or XML
    • Best For: Data migration, large-scale data operations

    Streaming API:

    • Use Case: Real-time event notifications
    • Protocol: Bayeux/CometD
    • Best For: Push notifications, real-time updates

    Metadata API:

    • Use Case: Deploy and retrieve metadata (custom objects, fields, Apex, etc.)
    • Best For: CI/CD pipelines, sandbox refreshes

    Tooling API:

    • Use Case: Build custom development tools
    • Best For: Debugging, code manipulation, metadata operations

    Q: What is the Salesforce Sharing Model and how does it work?¶

    A: The Salesforce Sharing Model is a multi-layered security framework that controls record access. It follows the principle of least privilege, starting restrictive and opening access as needed.

    Security Layers:

    Layer 1: Organization-Wide Defaults (OWD):

    • Private: Only owner and above can access
    • Public Read Only: All users can view, only owner can edit
    • Public Read/Write: All users can view and edit
    • Controlled by Parent: For master-detail relationships

    Layer 2: Role Hierarchy:

    • Users higher in hierarchy can access records owned by users below
    • Applies only when OWD is Private or Public Read Only
    • Does not apply to Contacts when OWD is Controlled by Parent

    Layer 3: Sharing Rules:

    • Owner-Based: Share records based on owner
    • Criteria-Based: Share records based on field values
    • Grant additional access beyond OWD

    Layer 4: Manual Sharing:

    • Owner can manually share individual records
    • Share button on record detail page
    • Temporary or permanent access

    Layer 5: Apex Managed Sharing:

    • Programmatic sharing using Apex
    • Create, query, and delete share records
    • Most flexible but requires code

    public class RobustExceptionHandling {

    public static void processAccounts(List<Account> accounts) {
        // Validate input
        if (accounts == null || accounts.isEmpty()) {
            throw new IllegalArgumentException('Account list cannot be null or empty');
        }

        Savepoint sp = Database.setSavepoint();

        try {
            // Step 1: Query related data
            Set<Id> accountIds = new Set<Id>();
            for (Account acc : accounts) {
                accountIds.add(acc.Id);
            }

            Map<Id, List<Contact>> contactsByAccount = queryContacts(accountIds);

            // Step 2: Process accounts
            List<Contact> contactsToUpdate = new List<Contact>();

            for (Account acc : accounts) {
                try {
                    // Process individual account
                    processAccount(acc, contactsByAccount.get(acc.Id));
                } catch (Exception e) {
                    // Log but continue processing other accounts
                    logError('Error processing account ' + acc.Id, e);
                }
            }

            // Step 3: Save changes
            if (!contactsToUpdate.isEmpty()) {
                Database.SaveResult[] results = Database.update(contactsToUpdate, false);
                handleSaveResults(results, contactsToUpdate);
            }

        } catch (QueryException e) {
            Database.rollback(sp);
            throw new ProcessingException('Query failed: ' + e.getMessage(), e);
        } catch (DmlException e) {
            Database.rollback(sp);
            throw new ProcessingException('DML failed: ' + e.getMessage(), e);
        } catch (Exception e) {
            Database.rollback(sp);
            throw new ProcessingException('Unexpected error: ' + e.getMessage(), e);
        } finally {
            // Cleanup code (always executes)
            System.debug('Processing completed');
            LimitMonitor.logLimits('After processAccounts');
        }
    }

    private static Map<Id, List<Contact>> queryContacts(Set<Id> accountIds) {
        Map<Id, List<Contact>> result = new Map<Id, List<Contact>>();

        List<Contact> contacts = [
            SELECT Id, AccountId, FirstName, LastName, Email
            FROM Contact
            WHERE AccountId IN :accountIds
        ];

        for (Contact con : contacts) {
            if (!result.containsKey(con.AccountId)) {
                result.put(con.AccountId, new List<Contact>());
            }
            result.get(con.AccountId).add(con);
        }

        return result;
    }

    private static void processAccount(Account acc, List<Contact> contacts) {
        if (acc == null) {
            throw new IllegalArgumentException('Account cannot be null');
        }

        // Processing logic
        if (contacts != null && !contacts.isEmpty()) {
            for (Contact con : contacts) {
                // Process contact
            }
        }
    }

    private static void handleSaveResults(Database.SaveResult[] results, List<Contact> contacts) {
        for (Integer i = 0; i < results.size(); i++) {
            Database.SaveResult result = results[i];

            if (!result.isSuccess()) {
                Contact failedContact = contacts[i];
                System.debug('Failed to update Contact ' + failedContact.Id);

                for (Database.Error error : result.getErrors()) {
                    System.debug('Error: ' + error.getMessage());
                    System.debug('Fields: ' + error.getFields());
                    System.debug('Status: ' + error.getStatusCode());
                }
            }
        }
    }

    private static void logError(String message, Exception e) {
        System.debug(LoggingLevel.ERROR, '### ERROR: ' + message);
        System.debug(LoggingLevel.ERROR, '### Exception Type: ' + e.getTypeName());
        System.debug(LoggingLevel.ERROR, '### Message: ' + e.getMessage());
        System.debug(LoggingLevel.ERROR, '### Stack Trace: ' + e.getStackTraceString());
        System.debug(LoggingLevel.ERROR, '### Line Number: ' + e.getLineNumber());

        // Optionally log to custom object for tracking
        createErrorLog(message, e);
    }

    private static void createErrorLog(String message, Exception e) {
        Error_Log__c log = new Error_Log__c(
            Message__c = message,
            Exception_Type__c = e.getTypeName(),
            Exception_Message__c = e.getMessage(),
            Stack_Trace__c = e.getStackTraceString(),
            Line_Number__c = e.getLineNumber(),
            Timestamp__c = DateTime.now()
        );

        try {
            insert log;
        } catch (Exception insertException) {
            // If logging fails, just debug
            System.debug('Failed to create error log: ' + insertException.getMessage());
        }
    }

    public class UserFriendlyErrors {

    public static void handleUserError(Exception e) {
        String userMessage;
        String technicalMessage = e.getMessage();

        if (e instanceof DmlException) {
            DmlException dmlEx = (DmlException) e;
            if (dmlEx.getDmlType(0) == StatusCode.REQUIRED_FIELD_MISSING) {
                userMessage = 'Please fill in all required fields.';
            } else if (dmlEx.getDmlType(0) == StatusCode.DUPLICATE_VALUE) {
                userMessage = 'A record with this value already exists.';
            } else {
                userMessage = 'Unable to save record. Please contact support.';
            }
        } else if (e instanceof QueryException) {
            userMessage = 'No records found matching your criteria.';
        } else {
            userMessage = 'An unexpected error occurred. Please try again.';
        }

        // Show user-friendly message
        ApexPages.addMessage(new ApexPages.Message(
            ApexPages.Severity.ERROR,
            userMessage
        ));

        // Log technical details
        System.debug('Technical error: ' + technicalMessage);
        System.debug('Stack trace: ' + e.getStackTraceString());
    }
}
